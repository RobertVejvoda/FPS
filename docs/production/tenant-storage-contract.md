# Tenant Storage Provisioning Contract

This document defines the provider-neutral tenant storage contract for FairSpot. It applies to all deployment profiles: local development, shared demo, and client-owned production.

The contract is technology-agnostic. Specific database vendors, Dapr component implementations, and connection strings are deployment-profile decisions. This document defines what every profile must satisfy regardless of the backing technology.

## Why This Matters Now

The FairSpot demo runs as a separate tenant sharing the same local infrastructure as development. This makes tenant storage isolation an immediate concern, not only a future production requirement. Any gap in tenant scoping visible in local or demo mode will carry forward to production.

## Tenant Identifier Rules

### Source of truth

Tenant identifiers must always come from authenticated claims or trusted service context. Request bodies, query strings, route parameters, and headers from unauthenticated or external callers must never determine the tenant storage boundary.

| Source | Permitted | Notes |
| --- | --- | --- |
| JWT `tenant_id` claim, validated by the service | Yes | Primary source for all user-facing requests. |
| Trusted service context (e.g., Dapr service invocation after mTLS) | Yes | Used for internal workflow and event processing. |
| Request body field supplied by an end user | **No** | The service resolves the tenant; the caller names itself within a validated tenant boundary. |
| Route parameter or query string not backed by a validated claim | **No** | Route parameters for entity IDs are acceptable; tenant selection is not. |

### Sanitisation rules

Before a tenant identifier is used in a storage key, collection name, partition name, index, backup path, or object storage prefix, it must be sanitised:

| Rule | Requirement |
| --- | --- |
| Character set | Lowercase alphanumeric and hyphens only: `[a-z0-9-]`. |
| Maximum length | 63 characters. This fits most database collection names, object storage prefixes, and DNS labels. |
| Minimum length | 3 characters. |
| Leading/trailing hyphens | Forbidden. |
| Case normalisation | Normalise to lowercase before use. JWT claim values may contain uppercase. |
| Reserved prefixes | `fps-`, `dapr-`, `admin-`, `system-` are reserved for internal use. Tenant IDs matching these prefixes must be rejected at provisioning time. |
| Collision handling | Two tenant IDs that produce the same sanitised form must be rejected. Provisioning must check uniqueness before creating storage. |

Example valid tenant IDs: `acme-corp`, `demo`, `t123`.
Example rejected: `ACME Corp` (uppercase and space), `fps-internal` (reserved prefix), `ab` (too short).

### Canonical sanitisation

Services must use a shared utility, not ad-hoc inline string manipulation, to produce tenant storage keys from tenant identifiers. A shared `TenantStorageKey` helper (or equivalent) must:

1. Accept the raw tenant ID from the authenticated context.
2. Apply the sanitisation rules above.
3. Throw or return an explicit error for identifiers that fail validation.
4. Return a stable, deterministic, normalised key for use in storage operations.

## Dapr State Store Key Rules

FairSpot services use Dapr state store for aggregate write state. Keys must make the tenant boundary explicit and must not allow one tenant's keys to overlap another's, even accidentally.

### Required key format

```
{entity-type}:{tenant-id}:{entity-id}
```

Every Dapr state key must include the sanitised tenant ID as an explicit segment. Entity IDs (GUIDs, request IDs, user IDs) alone are not sufficient, even if they are globally unique, because they do not make the tenant boundary legible or enforceable at the storage layer.

### Current key patterns and conformance

| Repository | Key pattern | Tenant-scoped | Notes |
| --- | --- | --- | --- |
| `DaprBookingQueryRepository` | `user-requests:{tenantId}:{requestorId}` | ✓ | Conforms. |
| `DaprBookingQueryRepository` | `pending:{tenantId}` | ✓ | Conforms. Tenant-scoped index; location/date filtering done in memory after load. |
| `DaprBookingRepository` | `count:{tenantId}:{date}` | ✓ | Conforms. |
| `DaprDrawRepository` | `draw:{tenantId}:{locationId}:{date}:{time}` | ✓ | Conforms. Generated by `DrawKey.ToStoreKey()`. |
| `DaprBookingRepository` + `DaprBookingQueryRepository` | `request:{tenantId}:{requestId}` | ✓ | Conforms. Migrated (DATA010). `TenantStorageKey.For("request", tenantId, requestId)` used throughout. |
| `DaprPenaltyRepository` | `penalty:{tenantId}:{requestId}:{penaltyType}` | ✓ | Conforms. Migrated (DATA010). |
| `DaprCorrectionAuditRepository` | `correction:{tenantId}:{requestId}:{timestamp}:{id}` | ✓ | Conforms. Migrated (DATA010). |

### Tenant-scoped component alternative

If the deployment profile uses tenant-scoped Dapr state store components (separate component per tenant, or per-tenant collection configuration), the component scoping is sufficient and individual key prefixing is not required for those components. The scoping choice must be documented in the deployment profile. Local and demo environments use a shared component, so key-level scoping applies.

## Tenant Storage Scope and Purge (PLAT002)

The shared-kernel `TenantStorageScope` (`FPS.SharedKernel.Infrastructure`) is the single, provider-neutral source of tenant storage identifiers. It reuses `TenantStorageKey` sanitisation and produces, from a trusted tenant key only:

- `Collection(service, tenantKey)` — deterministic `fps-{tenant}-{service}` collection / partition / schema-safe names.
- `KeyPrefix(entityType, tenantKey)` / `KeySegment(tenantKey)` — the Dapr state-key prefixes that scope a tenant's keys.

Callers never supply storage names directly. The **canonical storage key is the tenant id** — the same value services key their Dapr state under (`request:{tenantId}:…`) and that a purge scopes by. `TenantProvisioningMetadata` records the per-service scopes (Customer, Booking, Notification, Profile, Audit, Configuration, DataHub, legacy Reporting) derived from that tenant id, so provisioning evidence, service storage, and purge targets all match exactly. The tenant id is validated against this contract at provisioning time (3–63 chars, no reserved prefix); a generated GUID always conforms. `Collection()` is bounded to `MaxNameLength` (63) — a long tenant id is deterministically truncated with a short hash suffix, so a schema-based profile cannot overflow the identifier limit or collide.

**Tenant purge contract.** A single-tenant purge is defined by:

- `TenantPurgeScope.For(tenantKey)` — derived from the tenant key only; rejects blank/invalid input; exposes the key segment + per-service collections, all containing only that tenant.
- `ITenantStorePurger` — a per-service hook each store-owning service implements to delete its own tenant data for a scope. Stores holding immutable evidence (Audit) flag `IsImmutableEvidence`.
- `TenantPurgeOrchestrator` — platform-only; builds the scope, then invokes each purger. **Immutable-evidence stores are skipped unless an explicit sandbox/demo reset is requested**; normal GDPR erasure stays a separate path. Demo reset (#636) consumes this primitive.

## Service-Owned Read Model and Store Requirements

Each bounded context that persists data must satisfy the following provisioning contract:

### Booking

| Requirement | Detail |
| --- | --- |
| Write store | Dapr state store. All keys must use `{type}:{tenantId}:{id}` format (see gaps). |
| Index entries | User request index (`user-requests:{tenantId}:{userId}`) and tenant-pending index (`pending:{tenantId}`) are the primary query indexes. The pending index is tenant-scoped only; location/date filtering is done in memory. |
| Draw state | Draw keys are fully tenant-scoped via `DrawKey.ToStoreKey()`. |
| Backup scope | Tenant backup must restore all keys prefixed with `:{tenantId}:` across all key types. |
| Retention | See [Retention Schedules](../security/security-review-pack.md). Allocated bookings: 1 year. Rejected/cancelled: 90 days. |
| Provisioning evidence | Confirm state store component is bound and health-checked before serving tenant traffic. |

### Notification

| Requirement | Detail |
| --- | --- |
| Current state | In-memory repository (evaluation baseline). |
| Target | Tenant-scoped collection or partition in a persistent store. |
| Partition/collection key | `{tenantId}` or equivalent collection-level scoping. |
| Index | Recipient read index keyed by `{tenantId}:{recipientId}`. |
| Backup scope | Tenant collection or equivalent partition. |
| Retention | 90 days after creation. |
| Provisioning evidence | Collection/partition exists and is accessible before serving tenant traffic. |

### Audit

| Requirement | Detail |
| --- | --- |
| Current state | In-memory repository (evaluation baseline). |
| Target | Append-only, tenant-scoped collection or partition. No delete path on the audit record store. |
| Partition/collection key | `{tenantId}` or equivalent collection-level scoping. |
| PII mapping store | Separate collection/partition from audit records; this store supports deletion by actor hash for GDPR erasure. |
| Index | By `tenantId`, `occurredAt`, `action`, `actorHash`. |
| Backup scope | Tenant audit collection and PII mapping collection. Audit records must not be physically deleted by backup restore; erasure is through PII mapping deletion only. |
| Retention | 7 years or per jurisdiction. |
| Provisioning evidence | Append-only constraint documented; PII mapping store separately addressable. |

### Reporting

| Requirement | Detail |
| --- | --- |
| Current state | In-memory repository (evaluation baseline). |
| Target | Tenant-scoped collection or partition for metrics and fairness records. |
| Partition/collection key | `{tenantId}` or equivalent. |
| Index | By `tenantId`, `date`, `locationId`. |
| Backup scope | Tenant reporting partition. Fairness records may be anonymised rather than deleted for GDPR erasure. |
| Retention | 2 years. |
| Provisioning evidence | Read model store accessible before serving tenant traffic. |

### Profile

| Requirement | Detail |
| --- | --- |
| Current state | In-memory repository (evaluation baseline). |
| Target | Tenant-scoped collection or partition for profile and vehicle facts. |
| Partition/collection key | `{tenantId}` or equivalent. |
| Index | By `{tenantId}:{userId}`. |
| Backup scope | Tenant profile partition. |
| Retention | Active employee lifecycle; delete or anonymise on GDPR erasure request. |
| Provisioning evidence | Profile store accessible and health-checked before accepting employee requests. |

### Configuration

| Requirement | Detail |
| --- | --- |
| Current state | In-memory store for policy and slot data. |
| Target | Tenant-scoped collection or partition. |
| Partition/collection key | `{tenantId}` or equivalent. |
| Index | By `{tenantId}:{locationId}`. |
| Backup scope | Tenant configuration partition. Configuration is not PII-bearing; restore does not require GDPR considerations. |
| Provisioning evidence | Policy and slot data accessible and health-checked before serving booking traffic. |

### Customer

| Requirement | Detail |
| --- | --- |
| Current state | Dapr-backed. `DaprCustomerTenantRepository` (`tenant:{tenantId}`), `DaprCustomerIdentityRepository` (`identity:config:{tenantId}`, `identity:admins:{tenantId}`, `identity:index`), and `DaprCustomerParkingBootstrapRepository` (`bootstrap:{tenantId}`) are registered as the authoritative stores. `InMemoryTenantIdentityConfigStore` and `InMemoryTenantRoleMappingStore` are startup caches hydrated from persistent Dapr state via `HydrateIdentityStoresAsync()`. No in-memory class is registered as primary storage. |
| Scope | Owns tenant registry, onboarding state, and identity configuration. This service may need cross-tenant access for admin operations; it must use a separate admin store not accessible to per-tenant service accounts. |
| Tenant registry | One record per tenant, keyed by sanitised tenant ID via `CustomerStorageKey.Sanitise()`. Character set, length, reserved-prefix, and case-normalisation rules match the shared contract. |
| Provisioning evidence | Tenant record exists and readiness check (`TenantReadinessService`) passes — checks lifecycle, identity, admin, role mapping, parking policy, parking location, and out-of-process service health — before activating tenant traffic. |
| Implementation evidence (DATA010) | `DaprCustomerTenantRepository`, `DaprCustomerIdentityRepository`, `DaprCustomerParkingBootstrapRepository` registered in `Program.cs`. `CustomerStorageKey` enforces sanitisation rules; `CustomerStorageKeyTests` proves key format and rejection cases. `TenantReadinessServiceTests` proves all readiness checks and tenant isolation. `TenantIdentityServiceTests` proves hydration scenario (fresh stores populated from persisted config after simulated restart). |

### Object Storage

FairSpot uses object storage for tenant-owned binary content and generated evidence. Local and NAS profiles use MinIO; the DigitalOcean cloud follow-up may use Spaces where hosted object storage is needed. Client-owned production may use client-approved object storage or an S3-compatible equivalent as defined by the deployment profile.

| Requirement | Detail |
| --- | --- |
| Provisioning unit | Prefer one bucket/container per tenant where the provider supports it. A tenant-scoped prefix is acceptable for local/demo or constrained providers, but the deployment profile must document the isolation trade-off. |
| Naming | Bucket/container names must be derived from environment plus sanitised tenant business identifier, not raw tenant GUIDs. Example shape: `fairspot-{env}-{tenantKey}`. |
| Access boundary | V1 access is service-only. End users and clients access files through FairSpot APIs or signed URLs produced by FairSpot after authorization. |
| Object keys | Keys must include a controlled namespace and must not expose raw GUIDs as user-facing identifiers. Internal object keys may include opaque IDs when hidden behind catalog metadata. |
| Catalog | Every uploaded or generated object must have metadata in a FairSpot-owned catalog or owning bounded context. Object storage is not the permission or search layer. |
| Audit | Provisioning, upload, version publication, archive, delete, export creation, and branding changes must emit business audit records where relevant. |
| Traceability | Object metadata should record tenant ID, document/asset business ID, object key, content type, checksum, retention category, lifecycle status, uploaded/generated actor hash where relevant, trace/correlation ID, and timestamps. |
| Readiness | Tenant readiness should confirm the tenant bucket/container or prefix exists and can be written/read by the responsible service identity. |

Recommended namespaces:

| Namespace | Purpose |
| --- | --- |
| `tenant-documents/` | Controlled tenant documents such as policy PDFs, legal notices, consent notices, onboarding evidence, and HR import evidence where retention permits. |
| `reports/` | Scheduled reports and manually exported report files. |
| `audit/` | Audit evidence packages and draw lifecycle evidence exports. |
| `gdpr/` | Data export bundles and erasure workflow evidence. |
| `branding/` | Organization logo, favicon/app icon, and approved tenant display assets. |

Uploaded documents must enter object storage through FairSpot APIs, not direct MinIO/S3 user access. The upload API must validate caller role, tenant scope, document type, content type, file size, checksum, and retention category. Malware scanning is a production hardening hook and should be represented as a pending or configured validation step until a scanner is selected.

Organization branding assets use the same storage and catalog model, with stricter content validation. SVG should only be allowed if sanitised; otherwise prefer PNG or WebP. Clients must load branding through FairSpot client configuration, not through hardcoded bucket paths.

## Demo Tenant Isolation

The demo environment uses the same local infrastructure (Docker Compose, shared state stores) as local development. The following rules ensure demo tenant data does not bleed into developer data or vice versa:

| Rule | Implementation |
| --- | --- |
| Demo uses a fixed, distinct tenant ID | `demo` (sanitised) or configured equivalent. This must be different from `local`, `dev`, and any developer-provisioned test tenant. |
| All Dapr keys include the tenant segment | `user-requests:demo:...`, `draw:demo:...`, etc. A developer's test data uses their own tenant ID and cannot be reached by the demo tenant. |
| In-memory stores are process-scoped | In-memory stores do not survive restart, so demo-mode data is ephemeral. Multiple concurrent tenants in-process share memory (known limitation; not for production with concurrent active tenants). |
| Demo seed data loads only into its target tenant | `dev-seed.sh` and related fixtures must target an explicit tenant ID — `greenlogistics` for the seeded Green Logistics business data. Seed data must not omit the tenant parameter. |
| Demo IdP realm is separate from developer local realm | Keycloak demo realm and developer local realm must be distinct so demo users cannot authenticate as local accounts and vice versa. |
| Object storage paths are tenant-scoped | Demo must use a tenant bucket/container or a `demo/` prefix, not the object-store root. Demo document and branding flows must follow the same API/catalog model as real tenants. |

## Backup and Restore Implications

The following tenant storage contract requirements must be satisfied before backup/restore procedures are meaningful:

1. **Tenant-scoped keys and collections** must be in place so a targeted tenant restore can be performed without also restoring other tenants' data.
2. **Restore must validate tenant boundary** before applying data. A restore procedure must confirm the target tenant identifier in the backup matches the intended restore target.
3. **PII mapping store** is a separate restore scope. Restoring audit records without restoring the PII mapping state is valid for compliance purposes (pseudonymised records remain queryable by hash). Restoring the PII mapping state without the corresponding audit records is also valid.
4. **Object storage boundaries** must be tenant-specific. If per-tenant buckets/containers are used, restore operates on that bucket/container. If shared buckets are used, object paths must include the tenant ID in the prefix (e.g., `exports/{tenantId}/...`) so that single-tenant restores are possible.

See [Backup and Restore](./backup-restore.md) for restore order and evidence requirements.

| Gap | Severity | Detail |

All write and query read paths updated. |
| `penalty:{requestId}:{penaltyType}` in `DaprPenaltyRepository` | **Implemented (DATA010)** | Migrated to `penalty:{tenantId}:{requestId}:{penaltyType}`. `PenaltyDto` now carries `TenantId`. `IPenaltyRepository.ExistsAsync` now requires `tenantId`. |
| `correction:{requestId}:{...}` in `DaprCorrectionAuditRepository` | **Implemented (DATA010)** | Migrated to `correction:{tenantId}:{requestId}:{...}`. Uses `TenantId` already present on `CorrectionAuditDto`. |
| In-memory repositories for Notification, Audit, Reporting, Profile, Configuration | **Production-blocking** | These services use evaluation-grade in-memory stores with no persistent tenant storage. Each service requires a persistent, tenant-scoped store before production. |
| No shared `TenantStorageKey` sanitisation helper | **Implemented (DATA010)** | `FPS.Booking.Infrastructure.TenantStorageKey` validates character set, length, reserved prefixes, and normalises to lowercase. All three Booking key-type repositories now use it. Unit tests in `TenantStorageKeyTests` prove sanitisation rules and cross-tenant key isolation. |
| Demo seed data (`dev-seed.sh`) tenant parameterisation | Implemented (OPS007C) | `FPS_GL_TENANT_ID` (default `greenlogistics`) controls the tenant used by `dev-seed.sh` and `smoke-onboarding.sh`, which seed the Green Logistics business data. `FPS_DEMO_TENANT_ID` (default `demo`) still controls the Customer and Configuration service startup seed for the bare `demo` scaffold. | Object storage tenant provisioning and path enforcement | **Should fix before production** | MinIO or equivalent storage must be provisioned during tenant onboarding. Prefer one tenant bucket/container; otherwise enforce tenant prefixes. No enforcement currently exists. |
| Uploaded document catalog and authorization | **Should fix before production** | FairSpot has no document upload catalog yet. Uploaded documents must be stored through FairSpot APIs with metadata, role checks, retention category, checksum, and audit records. |

| Dapr state store component is shared across all tenants | **Acceptable for local/demo** | The local component is shared. This is acceptable while services enforce key-level tenant scoping. For production, evaluate per-tenant components or tenant-namespace support in the chosen provider. |
