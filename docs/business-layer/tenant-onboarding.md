# Tenant Onboarding

Tenant onboarding explains how a new company becomes usable in FPS. It is the business and implementation contract for creating the tenant, connecting identity, creating the first administrator, configuring parking resources, loading the minimum employee facts, and proving the setup before employees use the system.

This page complements [Customer Integration](./customer-data-import), which defines the SSO-first identity and profile-data contract. Tenant onboarding is the operational sequence that applies that contract to one company.

## Goals

Onboarding must answer these questions for every company:

| Question | Required answer |
| --- | --- |
| Which company owns this tenant? | A stable tenant record with display name, slug, lifecycle state, region, timezone, and support contacts. |
| Who may administer it first? | At least one tenant-scoped administrator or break-glass local account with audited creation. |
| How are users authenticated? | A trusted issuer/audience/tenant mapping, or an explicit local-account fallback for demo/small-tenant use. |
| Which roles are granted? | Tenant-scoped mapping from IdP groups or admin assignments to FPS roles. |
| Where can employees park? | One or more locations with policy defaults, optional overrides, and slots/capacity pools. |
| Which employees are eligible? | Minimal active profile facts needed for booking, notification, allocation, reporting, and support. |
| Is the tenant ready for live use? | A readiness check proves identity, policy, slots, demo users, notifications, audit, and reporting work for that tenant. |

## Lifecycle

Tenant lifecycle state should be explicit and auditable.

| State | Meaning | Employee access |
| --- | --- | --- |
| `Draft` | Tenant record exists, but setup is incomplete. | No live employee access. |
| `Configured` | Identity, first admin, default policy, and at least one location are configured. | Admin access only. |
| `Seeded` | Required employee/profile facts and slots/capacity are loaded or connected. | Optional pilot access for selected users. |
| `Ready` | Readiness checks pass and the customer accepts launch. | Employee access allowed. |
| `Suspended` | Tenant is temporarily blocked for business, security, or operational reasons. | No new employee actions. |
| `Archived` | Tenant is offboarded and retained only according to policy. | No access. |

State transitions must record actor, timestamp, reason, and readiness evidence where applicable.

## Onboarding Sequence

### 1. Create Tenant Workspace

Create the tenant shell before identity or employee data can be accepted.

Required fields:

- tenant ID generated by FPS;
- tenant slug used in operational tooling and collection naming;
- legal or display company name;
- primary region and data residency expectation;
- default business timezone;
- support and operational contacts;
- lifecycle state initially `Draft`.

Tenant creation must also prepare tenant-scoped persistence names or provisioning metadata for each service that stores tenant data. It must not require employee data yet.

### 2. Configure Identity And Role Mapping

Configure authentication before live employees can access FPS.

Required SSO configuration:

- trusted issuer;
- expected audience/client ID;
- deterministic tenant mapping;
- stable subject claim;
- group or role claim names;
- mapping from customer groups to FPS roles;
- deactivation behavior;
- fallback-account policy.

Unknown issuers, mismatched tenant claims, unmapped privileged roles, expired tokens, and missing stable subjects must fail closed.

### 3. Create First Administrator

Every tenant needs at least one administrator before HR/facility setup can proceed.

Allowed paths:

- mapped SSO user with administrator role;
- FPS-local break-glass administrator for demo, small tenant, or emergency use.

Local administrator accounts are fallback accounts only. Credential verifiers are Secret data owned by Identity. Creating, resetting, disabling, or privilege-changing a local account requires audit with actor, target user, tenant, reason, and timestamp.

### 4. Configure Parking Operations

Tenant administrators configure parking before employees submit requests.

Minimum setup:

- tenant default parking policy;
- at least one location;
- optional location policy override;
- slots or capacity pools for the location;
- timezone and cut-off behavior;
- company-car, reserved-space, accessibility, EV, motorcycle, and vehicle capability rules where relevant.

Policy and slot changes must create version/history evidence and audit records. Existing [Parking Policy Configuration](./parking-policy-configuration) remains the source of truth for policy fields and validation.

### 5. Load Minimal Employee And Profile Facts

Employees become usable through SSO-derived mapping, SCIM/provisioning, admin entry, or a tightly scoped bootstrap file.

Required minimum:

- tenant membership;
- stable external subject or local account identity;
- active/inactive status;
- FPS roles for privileged users;
- notification address only when needed;
- home location when policy or reporting needs it;
- vehicle, company-car, accessibility, reserved-space, and capability facts only where policy requires them.

FPS must not import customer passwords, broad HR records, medical details, or unrelated employee data. File/bootstrap import remains an exception path and must follow [Customer Integration](./customer-data-import).

### 6. Readiness Check

Before the tenant moves to `Ready`, FPS should produce a readiness result that can be shown to the customer or operator.

Readiness checks:

- tenant is not `Draft`, `Suspended`, or `Archived`;
- identity issuer and audience validate against a sample token or configured test identity;
- at least one administrator can authenticate;
- role mapping grants no unmapped privileged role;
- tenant default policy is valid;
- at least one active location has active slots or capacity;
- required profile facts exist for the pilot users;
- Booking can submit a test request for a pilot user without caller-supplied tenant/user IDs;
- Notification can create or route an operational notification for the tenant;
- Audit records tenant setup and readiness events without raw secrets or unnecessary PII;
- Reporting can query tenant-scoped summary data without crossing tenant boundaries.

Readiness checks may run in dry-run mode for client evaluation. Dry-run output must not include secrets, tokens, raw credentials, or broad employee data.

## Tenant Setup Data

| Data | Owner | Classification | Required before `Ready` |
| --- | --- | --- | --- |
| Tenant identity, slug, display name, lifecycle state | Customer service | Confidential | Yes |
| Region, timezone, support contacts | Customer service | Confidential | Yes |
| Trusted issuer, audience, subject mapping | Identity service | Confidential | Yes for SSO tenants |
| Client secrets, integration credentials | Secret store / Identity | Secret | Only when integration flow needs them |
| Role/group mapping | Identity service | Confidential | Yes |
| First administrator mapping | Identity/Profile | Confidential | Yes |
| Parking policy and location overrides | Configuration service | Internal/Confidential | Yes |
| Slots or capacity pools | Configuration service | Internal | Yes |
| Employee subject mapping and active status | Identity/Profile | Confidential | Yes for pilot/live users |
| Vehicle/company-car/accessibility facts | Profile service | Confidential, sensitive where applicable | Policy-dependent |
| Readiness evidence | Customer/Operations | Internal/Confidential | Yes |

## Out Of Scope For First Tenant Onboarding

- billing and subscription enforcement;
- custom HR-system integration beyond the documented minimal contract;
- SCIM lifecycle automation unless explicitly chosen for a customer;
- migration of broad historical parking data;
- client-specific identity-provider adapters that cannot be expressed through OIDC configuration;
- production offboarding and data-retention automation beyond recording lifecycle state and evidence.

## Acceptance Criteria

- A new company can be represented as a tenant before any employee data is imported.
- Live employees cannot authenticate until trusted issuer/tenant mapping is configured or an explicit local-account fallback is enabled.
- At least one tenant administrator exists before parking configuration is marked complete.
- The tenant cannot become `Ready` without valid policy, at least one usable location/slot capacity, and required pilot user/profile facts.
- Tenant setup changes are auditable and tenant-scoped.
- Secrets and credentials are never stored in docs, issues, logs, import files, or non-secret persistence.
- The setup sequence can be followed by an operator or tenant admin without reading implementation code.
